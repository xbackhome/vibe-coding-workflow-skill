# SDD + TDD 执行规则

SDD 在这里指规格驱动开发（Spec-driven Development）。Vibe Coding 工作流覆盖调研、需求、设计、实施与交付；SDD + TDD 是其中复杂功能的实施方法。

## 按任务选择深度

先按主文档的需求清晰度、影响范围、错误代价和会话跨度判断，再选择下表的方法。已有清楚规格时直接引用；一份文件可以同时承载简短规格与实施记录，无需为每个阶段新建文档。

| 任务 | 规格与验证要求 |
| --- | --- |
| 新建长期维护的产品、复杂功能、多模块行为变更 | 使用明确规格、验收条件和逐步 TDD，最后单独对照规格验收。 |
| 范围明确且单会话能完成的功能 | 使用简短范围、关键规则和验收条件，逐项实施；可复用现有规格与测试，不必单独建立任务追踪。 |
| 清晰的小行为改动或 Bug | Bug 先复现症状与定位原因，再针对真实回归风险增加失败测试；可复用现有规格或写简短预期，不必建立整套文档。 |
| 文档、低影响配置或纯视觉微调 | 使用适合改动的检查和实际操作；不强制新增完整规格或测试套件。 |
| 探索性原型 | 先验证假设。原型转为长期维护实现时，重新确认规格与验证方式。 |

## 1. 建立规格基线

按适用的项目调研规则寻找相似项目并澄清需求与范围，再把已经确认的内容写入规格。已有明确规格时沿用并记录本次变更。规格至少说明目标、包含与排除的内容、业务规则、约束、关键异常和验收条件；候选功能、未解决决策与暂定假设分别标记，不能补写成确定需求。

给验收条件稳定编号（例如 AC-01）。描述外部可观察结果，而不是预设某个类名或函数数量。记录规格路径与版本；实现计划引用规格，不再创建另一份相互竞争的需求。

实施前对照适用规则、长期术语、ADR 与相关实现。记录冲突来源及适用范围，区分需求变化、过期文档、实现偏差；既有代码不自动成为应遵循的业务要求。按适用的指令与项目规则处理，影响核心范围或重要约束的取舍由用户决定，未解决时先完成不依赖它的工作。

发现需求矛盾或需要改范围时，先说明变更原因、原条件与新条件，再解决决策，并同步受影响的验收条件、测试和计划。规格可以由 Agent 起草或整理已确认决定，不能单方面删改需求来迎合现有实现。每次实质变更保留版本或可定位的变更记录。

### 维护任务的规格变更

区分当前规格基线与本次目标变更，引用已有文档，不整份重写无关需求。当前代码可能偏离规格，应作为实现偏差调查，不能自动写成新的业务要求。

记录变更类型（新增、修改、删除）、原条件与目标条件、原因、确认来源、受影响的接口或行为，以及需要调整的任务、测试和验收方法。保留未受影响的条件与约束。小改动可在同一工作记录写几行；复杂或跨会话工作再单独组织文档，沿用项目现有路径，不要求 OpenSpec 的目录或 CLI。

用户确认的目标变更指导实施，记录基线版本与目标版本或可定位的变更标识。验收通过后，将已交付变更整理进后续规格版本并保留历史；失败、未验证或暂缓的部分保留相应状态，不能描述成已实现现状。删除需求时明确目标行为及关联检查如何变化，仍保留其他必需行为的回归验证。

### 需求、计划、任务与验证的一致性

实施前及实质需求变更后检查：

1. 每条必需需求是否有实施安排，或已有实现满足它的证据？
2. 每项任务是否来自需求、明确约束或有理由的必要技术工作？没有依据的功能不能混入实施。
3. 每条验收条件是否对应自动测试或明确的人工方法？是否覆盖重要边界与异常？
4. 规格、计划、任务、测试与验收表是否针对同一目标版本？变化的条件及关联内容是否同步？

逐项记录缺失、矛盾和无依据的范围并处理，不为制造对应关系编造需求或证据。短任务可用一份记录中的条目完成，不要求独立计划、任务文件或额外任务编号。文档检查证明对应关系是否清楚，不能证明实际产品已经通过验收。

## 2. 从验收条件设计测试

为每条条件指定自动测试或人工验收方式，包含能影响结果的边界与异常。优先选择能验证目标行为的最简单测试层级；跨模块流程需要集成测试，真实界面流程可用端到端检查或明确的人工步骤。

测试观察业务结果，不机械复述实现，也不只验证 mock 被调用。需要替代网络或其他外部边界时，保留真实的被测逻辑。没有稳定自动化接口的体验要求可以人工验收，但要明确步骤和完成状态。

把关键测试观察点写清楚：通过哪个公开接口或用户操作观察什么结果。沿用已有且能证明行为的测试，避免为同一行为重复建套件；普通测试细节由 Agent 根据项目约定选择，重要接口取舍或行为歧义需要先解决。

规则复杂、异常易遗漏或跨模块时，按需用“前提—操作—预期结果”描述场景，补足模糊的验收句子。只有在场景能明确行为或暴露歧义时使用，不要求每条条件机械套格式。例如：前提是已导入一本书；操作是删除原始文件后重新打开；预期结果取决于已确认的存储方式——复制进书库时仍可阅读，引用原文件时显示明确的缺失提示。先确认存储方式，再保留对应的确定场景，不能把两种结果都当作随意可选的通过条件。

例如：

| 条件 | 测试或验收方式 |
| --- | --- |
| AC-01：导入有效 UTF-8 TXT 后展示其正文 | 在导入边界验证有效文件被读取并得到正确正文。 |
| AC-02：不符合约定格式的文件被拒绝并显示原因 | 为拒绝行为建立可重复测试。 |
| AC-03：用户能完成导入、阅读和关闭流程 | 操作运行中的产品并记录结果。 |

先规划测试场景，再逐个添加和运行；不要先写完所有测试再一次性生成整项功能。

## 3. 小步 RED → GREEN → REFACTOR

1. **RED**：选择一个尚未实现的验收行为，先写测试并实际运行。确认失败来自行为缺失或错误，而不是语法、环境或测试数据问题。已有实现刚好满足测试时，记录现有证据，不人为破坏代码制造失败。
2. **GREEN**：只实现让当前测试通过所需的最小改动。运行该测试和必要的回归检查；不通过时诊断并修复，不为迎合错误实现随意削弱断言。
3. **REFACTOR**：测试通过后再消除重复、改进命名与结构，保持行为和验证结果不变。不要借重构增加范围外功能。
4. 重复以上循环，直到当前小功能满足相关验收条件。记录实际失败与通过的结果；实现后才补的测试属于补充验证，不能声称已经执行 TDD。

环境无法执行时，明确列出缺失条件和未验证项。不要伪造失败、通过或人工验收记录，也不要为了补造 TDD 历史删除无关代码或已有用户工作。

Bug 修复先取得原始症状与原因证据，再用真实回归风险选择测试。无法复现时说明原因假设、已经观察到的证据和进一步诊断办法；修改看似合理不能作为症状已修复的证据。

## 4. 审核实际改动并处理意见

实施结束后先确认审核输入：规格路径与版本、比较基点、相关文件、改动状态与实际差异。覆盖本次相关的已提交、暂存和未暂存修改；隔离用户已有的无关工作。只读取提交差异的审核工具看不到工作区改动时，使用支持实际差异的审核方式，或在已有授权与项目流程允许时安排 Git 里程碑。不能为满足审核工具擅自提交。

分别审核两方面：

- **规格符合性**：必需行为是否遗漏或错误，是否有额外功能，是否违反约束，验收证据是否覆盖真实结果。
- **代码质量**：是否复用已有实现，数据流和命名是否清楚，是否有重复逻辑、无依据的兜底或吞异常、为假想需求预设的抽象。判断依据来自适用规则、实际风险和代码，不将风格偏好自动当成缺陷。

每项发现记录依据、影响和处理：修复、据证据驳回、用户确认延期或待决。修复后复验受影响行为与必要回归；阻塞交付的问题未解决时保留阻塞状态。延期不等于通过，仍影响必需验收条件的问题要在交付中明确。

优先沿用同一改动版本与已覆盖范围的审核结果。出现新修改后，对新增差异和受影响行为补充审核，避免重新打开已解决且证据仍有效的问题。复杂或高影响工作在能力与授权允许时可使用独立审核；缺少相关能力时说明实际由谁检查，不伪造独立审核。

## 5. 对照规格验收并留档

测试通过后，逐条核对当前目标规格：有无遗漏、额外功能、违反约束的实现，以及自动测试没有覆盖的体验。检查需求、实施结果和证据的对应关系；每条条件记录通过、失败或未验证及其证据。需求变化后重新检查受影响的任务与验证，保留其他仍有效的结果。实际改动尚未验证时，材料一致或任务打勾也不能作为通过证据。

需要用户访问或判断时，交付可检查的结果与操作步骤，并请求实际体验。必要条件仍失败或未验证时，标明部分交付或待验收，不宣称完整验收。自动检查通过、审核执行过或 Git 已提交，都不能单独证明产品验收完成。

分别记录实施状态、审核意见处理状态与验收状态。通过必需条件后，依据项目流程和已有授权更新任务记录或关闭任务；外部任务更新、提交或发布仍遵守相应授权。审核发现修复后更新相关证据，保留其余仍有效结果。

交付状态明确后，按规格变更规则整理已交付内容与后续版本，保留变更原因和历史定位。部分交付只整理已验收部分，其他目标仍标记待处理，避免把整个提案写成已交付。

在已验证的功能节点按用户授权与项目习惯提交 Git。交接时注明实际分支和工作状态，不因为工具默认会提交就扩大授权。

交付时给出规格版本、验收表、测试结果和人工验证结果；不用 Token 数量、测试数量或覆盖率单独代替完成证据。

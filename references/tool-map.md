# 按任务选择工具

按任务所需能力选择工具，并适配用户当前使用的 Agent 应用。文中包含原始材料中的工具示例和后续核查的参考项目，均按需要选择；同类工具或当前应用的内置能力可承担相应任务。软件功能会变化，做具体推荐前查看上游文档。

## 适配当前 Agent 应用

先从当前可见的工具、配置和项目环境确认实际能力：能否访问目标代码、编辑文件、运行命令和测试、联网检索，以及操作浏览器或桌面。IDE、命令行、桌面和云端应用按各自实际能力分配工作；仅能对话的助手可用于讨论、规格和操作指导。应用名称本身不能证明具备某项能力。

优先沿用用户已选择且能满足任务的应用。一款应用可以覆盖多个阶段，也可以由多款工具接续；确有能力缺口时，说明需要补足的能力与交接方式，再按用户偏好选择。无法直接操作时，给出可执行步骤，由用户执行并提供结果；获得结果前保留“未验证”状态。云端执行得到的结果应注明实际环境，涉及用户本机的行为仍需在目标环境验收。

跨应用交接时，保留规格版本、相关文件或设计稿、下一步任务、验收条件和已有验证证据。只在不同应用的规则发生冲突或确实影响执行时，补充适配说明。

## 任务与能力对应表

| 需要解决的问题 | 所需能力与可选示例 | 使用方式与边界 |
| --- | --- | --- |
| 项目初期需要头脑风暴，或想法模糊 | 当前应用的对话与需求分析能力，例如 ChatGPT 或其他对话式助手；按需参考已安装的 brainstorming Skill | 人机讨论优点、缺点、关键风险、遗漏的场景和想法，比较替代方案；先统一术语，再确认流程和范围。候选想法经确认后才进入规格。 |
| 需要跨多个来源做市场、用户或竞品研究 | 当前应用的联网检索或研究能力，或外部研究工具；例如 ChatGPT Deep Research | 给出明确的研究问题和来源范围，核对报告引用，将有证据的结论与假设分开。快速问题直接搜索或对话即可；无检索能力时让用户提供来源，不能编造引用。 |
| 新想法、项目调研或审核，以及规划、架构、技术、依赖或实施路径选择 | 当前上游仓库与联网检索能力；已安装时加载 `project-open-source-scout`，否则按[开源项目匹配规则](open-source-scout.md)调研 | 在推荐方案前给出有来源的中文高匹配清单，核对功能、维护、许可证和部署约束；将采用决定交给讨论、审查、规格与计划。清楚的局部维护不重复调研。 |
| 建立可维护的项目基础 | Git、AGENTS.md、CONTEXT.md、ADR 等项目文档 | 用 Git 记录已验证的功能节点；把长期规则、术语与重要架构决策写入适合的文档，并定期清理冲突或过期内容。 |
| 界面质量或交互复杂度高 | 当前可用的设计、原型或界面生成工具，例如 Google Stitch；具备相应代码编辑能力的 Agent | 探索并确认界面，再把设计稿、设计规则和交互要求交给 Agent 实现。能读取设计图时直接使用，不能读取时提供文字规格或可访问的设计文件；运行后逐屏比较和修正，不把“一比一复刻”当作自动保证。 |
| 编写代码、修改现有项目 | 能访问目标代码并编辑文件的 IDE、命令行、桌面或云端 Agent；例如 Codex、Claude Code、OpenCode、Pi、Cursor | 给 Agent 规格、项目规则、相关代码和验收条件；以实际可用能力选择执行方式。仅能对话时提供代码改动说明，由用户应用；不能宣称已写入仓库。 |
| 浏览器或桌面应用需要自测 | 当前 Agent 或配套工具的测试、浏览器／计算机交互能力；必要时才添加相应插件 | 按当前可用能力操作真实流程并记录证据，再由用户判断实际体验。无界面操作能力时提供人工验收步骤；不能只看代码就宣称完成。 |
| 简单功能或小型修复 | 当前 Agent 的代码检查与执行能力；必要时使用诊断或需求澄清 Skill | 沿用清楚需求。Bug 先复现与定位，存在真实回归风险时建立测试；不会改变结果的问题不进入讨论。Matt 的 grill-me、diagnosing-bugs 或 implement 仅在相应能力、配置和调用方式可用时使用。 |
| 新产品或复杂功能需要明确实施方法 | SDD 规格与验收表、项目已有测试框架；按需使用已安装的 TDD Skill | 从已确认的验收条件拆测试，逐个执行失败测试 → 最小实现 → 重构，再逐条对照规格验收。无需为了采用 SDD+TDD 安装整套框架。 |
| 多轮、复杂且术语容易混乱的功能 | Matt Pocock Skills 中的 grill-with-docs → to-spec → to-tickets → implement | 采用完整流程时检查 setup-matt-pocock-skills 的项目配置是否已经完成，仅补缺失配置。单会话能完成的工作可跳过独立规格与拆票步骤，仍保留适合的验收依据。implement 会调用 code-review；检查实际审核范围、意见处理与验收状态，不把调用成功视为全部交付完成。 |
| 希望使用成套工程流程的新产品或复杂改动 | Superpowers | 依据当前版本选择探索实验、范围明确的改动或架构性路径，核对其确认与实施要求。可选当前会话内实施或逐任务独立 Agent 实施；按照工作影响、能力、授权和成本选择。 |
| 目标过大、路线尚不清楚，或已有架构阻碍维护 | Matt Pocock Skills 中的 wayfinder、improve-codebase-architecture；术语难懂时用 wait-what | 只在出现相应问题且已具备所需项目配置时使用；不要为普通功能强制加载全套技能。 |

安装或启用外部 Skill、插件或 Agent Skill 前，先读取适用的用户与项目规则，并在目标环境对实际待安装包执行其要求的安全扫描与授权检查；这份工具表本身不触发安装。

## 从参考项目按需借鉴方法

以下方法已融入本 Skill 的现有指南，可由当前 Agent 执行；项目名称说明借鉴来源，不构成工具依赖。无需为了使用这些方法安装框架、运行专用命令或生成完整的文档目录。

| 来源 | 已吸收的方法 | 何时使用 | 在本 Skill 中的位置 |
| --- | --- | --- | --- |
| OpenSpec | 规格基线与本次变更分开，明确新增、修改、删除及影响，验收后整理已交付内容并保留历史 | 修改已有行为或持续迭代；小改动写几行即可 | [规格变更规则](sdd-tdd.md)、[工作记录](working-note.md) |
| Spec Kit | 检查规格、计划、任务、实现和验收证据的一致性 | 有明确需求的实施与验收；使用现有材料即可 | [一致性与验收规则](sdd-tdd.md) |
| BMAD | 按当前问题切换用户、产品、技术、测试视角，发现需求与验收缺口 | 新想法或复杂且不清楚的功能；局部维护只选有关视角 | [人机讨论指南](brainstorming.md) |
| Spec Kit（可选） | 基于证据给出进入开发、补证或实验、暂缓或放弃的建议 | 用户尚未决定新想法是否值得投入 | [想法评估](brainstorming.md) |
| OpenSpec（可选） | 用前提、操作、预期结果描述验收场景 | 规则有歧义、异常易遗漏或跨模块；清晰句子无需改写 | [场景化验收](sdd-tdd.md) |

本 Skill 不复制这些项目的完整角色体系、命令链、安装器、多仓库共享存储或自动同步机制。只有用户需要实际接入相应工具时，才核查当前上游版本、配置、授权和安全要求。已有头脑风暴、TDD 和任务分级直接沿用，避免叠加同类流程。

## 接入外部工作流程

本 Skill 自身提供讨论、规格、实施与验收规则，可以在当前 Agent 中执行。外部 Skills 是可选方法或执行入口，采用时先检查实际安装版本、可调用入口、所需配置和当前用户授权。引用上游概念不意味着必须安装整套工具。

同一阶段选定一个主要执行流程，交接已有合格成果；避免同时启动两套头脑风暴、两份规格或重复审核。已启用的外部流程有明确要求时，使用它支持的入口或配置进行适配；要求与当前任务冲突且无法适配时，说明冲突并按适用指令执行，不承诺所有流程能够透明组合，也不擅自改动外部安装文件。

以下为 2026-09-29 核查上游所得的接入注意事项，执行时以实际安装版本为准：

- **Superpowers**：brainstorming 已区分探索、范围明确和架构性工作，但各路径仍有相应确认要求。executing-plans 提供当前会话内实施和最后集中审核，减少逐任务重新读取上下文的成本；独立审核和子 Agent 实施仍取决于实际能力与授权。
- **Matt Skills**：grilling 当前支持将相互独立的问题合并成一轮，也支持用户偏好的逐项节奏。先查事实再询问决策；采用它的完整流程时保留共享理解的确认要求，已经明确的用户决定不重复询问。
- **Matt 的实施与审核**：implement、to-spec 等入口在当前上游设置为用户主动调用，不能假定本 Skill 能自动调用；按目标应用提供正确入口和下一步。implement 默认提交当前分支，并调用 code-review；先核对其行为是否符合已有授权。code-review 当前以固定基点到 HEAD 的提交差异为输入，工作区和暂存区修改需通过适合的审核方式纳入，不能漏检。审核意见的修复、复验和产品验收按本 Skill 继续处理。

## 控制流程成本

当前 Agent 能完成的事实查找、代码修改和常规检查直接完成。复杂或高影响工作确需独立视角时，在授权范围内引入审核 Agent；缺少能力时说明由当前 Agent 检查及独立性限制。需要并行实施时先划定文件与任务范围、隔离共享 Git 状态；并行能力本身不构成调用授权。

已经确认的资料、规格与同一版本的审核结果通过引用复用。修复后检查新增差异、受影响行为与必要回归，证据仍有效的部分不重复执行。实际出现相关文档冲突或过期内容时整理，不把全库文档清理加到每次小改动中。

评估实际使用效果时，关注重复提问、额外功能、恢复后重复开发、漏检改动和缺失验收证据。时间、轮次或用量可在确有数据时记录；没有用量数据就注明不可用，不承诺固定节省比例。

# 复杂 Bug 诊断规则

适用于偶发、难复现、跨组件或性能问题。症状和原因都已明确的局部 Bug，沿用主流程即可。

## 先建立故障反馈方式

1. 记录用户实际观察、预期结果、输入、运行环境及首次出现范围；把原因猜测与观察分开。展示日志或请求时先隐藏凭据和个人数据。
2. 找到能显示**原始症状**的最小反馈方式：已有测试、单条命令、运行中的界面操作、可重放输入或必要的人工步骤。优先复用项目现有能力，不为诊断引入不必要的工具。
3. 缩短反馈耗时并提高稳定性：固定输入、时间或随机种子，隔离无关外部状态；断言具体错误结果，而不只检查“没有崩溃”。偶发症状仍出现不稳定时，记录出现次数和条件，不把一次未出现当成修复成功。

## 用证据定位并复验

针对可区分的原因假设，逐项检查代码路径、日志、版本差异或最小实验；一次只改变足以辨别假设的条件。找到原因后做最小修复，重新运行原始反馈方式和相关行为检查；有实际回归风险时保留相应测试。

无法获得可靠反馈方式时，说明已观察的证据、仍可能的原因、下一步需要的输入或权限。可以修复已证实的独立问题，但不能将推测性改动报告为原始症状已解决。

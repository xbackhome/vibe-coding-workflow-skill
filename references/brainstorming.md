# 项目初期的人机头脑风暴

适用于新项目、价值与范围尚不清楚的想法，或存在重要选择的复杂功能。目标是共同发现项目价值、弊端和缺口，再决定第一步；不要在已有清楚规格的小维护任务中重新讨论整个产品。

## 整理原始描述与术语

先读取用户提供的描述、已有项目资料和相关实现，回述目标、主要场景与限制。清楚的内容直接沿用；混乱口述先整理，不为填满文档补造需求。

有歧义的术语记录原始说法、候选别名、定义、包含与排除范围、确认状态。例如“打开文件”可能只显示正文，“导入书库”可能涉及永久保存或复制文件；只有用户描述或项目证据支持时才合并两者。优先解决会改变范围、数据含义或行为的歧义，不要求为每个普通词创建术语条目。

区分四种状态：**已确认、待用户决定、明示的暂定假设、已排除**。已确认内容进入规格；暂定假设写出依据与验证办法，不转换成确定需求。影响核心行为的假设需要用户决策或实验结果，普通可逆实现选择按既有授权处理并说明依据。

## 讨论方式

1. **理解原始想法**：让用户用自己的话说目标、痛点和理想结果。先查看已有项目资料，避免重复询问。统一有歧义的术语；形成讨论范围所需的基本理解后，按[开源项目匹配规则](open-source-scout.md)执行 `project-open-source-scout` 或等价调研，再进行具体采用、设计或技术决策。
2. **讨论优点与价值**：谁会受益、在哪个场景下、相较现有做法改善什么？区分用户的实际经验、有出处的证据和暂未验证的假设，不把 AI 的赞同当成市场验证。
3. **主动发现弊端与问题**：提出会影响项目成败的反例、约束和成本。按项目实际情况讨论需求频率、使用门槛、技术可行性、维护负担、数据与集成等因素，不机械列出与项目无关的风险。说明依据和影响；不把猜测写成事实，也不为想象中的极端情况堆功能。
4. **查找缺失的想法与场景**：询问哪些用户、关键操作、异常或替代做法尚未考虑；提出有理由的补充想法。分别标记必须补齐的缺口、值得实验的假设和可延期的增强，不把所有新点子都塞进第一版。
5. **比较可行路径**：存在真正不同的选择时，给出少量方案，解释价值、代价和限制，说明推荐理由。用户可以修正、否定或补充；AI 应围绕具体依据讨论，而不是只赞同或反驳。
6. **收敛为决策**：总结双方已经确认的价值与范围、接受的取舍、剩余关键风险，以及验证风险的最小实验。把想法标为采用、延期或放弃；只有确认的需求进入 SDD 规格。

当讨论暴露出项目可能缺少实际价值、要求互相冲突或关键能力难以实现时，按[项目与想法合理性审查](idea-audit.md)核对证据并形成明确建议。用户直接要求审核已有项目时，也可以从该指南开始，不必重新进行完整头脑风暴。

## 按问题选择讨论视角

新项目或复杂且需求不明确的功能，按实际疑问切换视角；局部维护只检查与改动有关的部分。一个 Agent 在同一对话中即可完成，不默认召开多角色会议或调用多个 Agent。

| 视角 | 检查的问题 | 可保留的结论 |
| --- | --- | --- |
| 用户 | 谁在什么场景遇到什么困难？现有替代做法是什么？ | 核心使用流程、实际痛点、体验要求 |
| 产品 | 哪些结果必须在首版实现？哪些想法可以延期？ | 首版范围、优先级、明确排除内容 |
| 技术 | 当前环境能否实现？已有能力能否复用？集成与维护成本在哪里？ | 可行路径、约束、重要取舍或待验证假设 |
| 测试 | 怎样观察成功和失败？关键规则及异常如何验证？ | 可验证的验收条件、测试观察点或人工步骤 |

不同视角发现同一问题时合并讨论并引用已有答案，不为填满表格重新提问。只有会影响当前决策的缺口进入澄清。

## 筛选问题与控制讨论节奏

提问前逐项检查：

1. 是否能通过现有资料、代码、工具或上游来源自行查明？能查的事实先查，查不到时说明缺口。
2. 是否已经回答、已有明确约束，或被本次范围排除？引用原决策，只在出现新证据或用户改变范围时重新打开。
3. 不同答案是否会改变实施、验收或重要取舍？仅影响遥远扩展的问题记入延期事项。
4. 是否依赖另一项尚未确定的答案？依赖问题后问，避免让用户选择前提尚未成立的方案。

依赖前一答案的问题逐项问；相互独立的问题可少量合并成一轮。优先提供清楚的选项、推荐依据和取舍，保留自由补充空间。用户偏好逐项讨论时遵循其节奏。选项应对应真实差异，避免通过选项偷偷加入功能。

每轮更新已确认结论与排除事项，并检查业务目标、主流程、业务规则、关键异常、验收边界和矛盾。问过多少次只用于观察讨论成本，不作为必须完成的指标。原始材料中的“30 + 20”可在用户指定时作为检查提醒；更早已明确时就结束，达到预算仍有阻塞决策时汇总问题并保留待决状态。

被范围排除的情况仍需区分输入边界。例如“只支持 UTF-8”排除了多编码自动识别，但不一定回答了不支持输入时如何提示；只澄清会影响交付的处理行为。

## 何时结束讨论

核心用户、价值、主流程和第一版范围已经能够说明，关键矛盾已解决；对剩余不确定性有明确验证办法时，就可以整理规格或先做实验。结束条件不是耗尽所有可能的问题，也不是确保项目没有任何风险。

停止提问后总结已确认范围、明确排除内容、剩余假设和下一步。用户只要求讨论或方案时交付结论；已经授权实施且关键决策已解决时，继续执行范围内的工作。新的重大需求或取舍由用户决定，既有确认无需逐阶段重复索要。

无法通过讨论判断外观、体验或可行性时，明确观察问题、最小原型和结果判据，再用实际证据解决。原型探索与正式产品范围分别记录。

## 按需评估是否进入开发

只在用户仍在判断新想法是否值得投入时使用。综合目标用户、替代方案、实际需求证据、成本与关键未知，给出以下一种建议及理由：

- **进入开发**：已有依据支持一个明确、可验收的首版，说明仍需验证的假设；这不代表市场已经验证成功。
- **补充证据或做实验**：关键价值、体验或可行性尚不确定，明确需要什么证据、最小实验及结果判据。
- **暂缓或放弃**：当前证据或约束不支持投入，说明理由及未来可以重新评估的条件。

最终选择由用户决定；AI 建议不自动取消或扩大已经授权的任务。小维护任务和已确认要实施的功能不重复评估整个产品价值。选择进入开发后只交接已确认范围与待验证项，不把评估报告再复制成另一套需求。

## 保存结论与恢复讨论

跨会话、重要决策或多条相互影响的规则，使用[工作记录模板](working-note.md)。重要决策确认、一轮讨论结束、阶段或 Agent 切换前增量保存；只更新有变化的条目，引用已有规格和证据。没有文件编辑能力时，交付可复制的记录并请用户保存，不声称已经落盘。

保存简短的探索结论：

- 已确认的目标用户、问题和价值。
- 主要优点与弊端，以及依据或待验证假设。
- 最重要的缺失场景或想法及处理决定。
- 选择的方案、接受的取舍、延期或放弃的内容。
- 剩余关键疑问、验证办法，以及下一步是写规格、做实验还是停止。

恢复时先读取上述记录，并核对实际项目文件；从尚未确定的问题继续。发现记录相互矛盾时定位来源，不能根据压缩后的对话记忆重写已确认决定。

## 对话启动示例

> 我有一个项目想法：【想法】。先不要写代码。请先理解目标用户和核心场景，再与我逐项讨论优势、弊端、重要风险和遗漏的想法。问题尽量给出选项，说明你的判断依据；有不同方案时比较取舍。把已确认内容与候选点子分开，最后整理第一版范围、待验证假设和下一步。
